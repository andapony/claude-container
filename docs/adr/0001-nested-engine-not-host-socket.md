# 1. Agents get a nested container engine, never the host's

Date: 2026-10-14

## Context

Some projects (andapony/tea42 first) deliver a Docker image as their run
environment. Agents in the claude-dev container have to write its
Dockerfile, build it and test it unattended. Later the human rebuilds it
on the Mac with OrbStack's Docker.

The obvious way to give an agent `docker` is to mount the host's socket.
But the host's engine controls every container on the Mac, and that
includes the mail container, which holds OAuth tokens and app passwords.
With the socket an agent could `docker exec` into it, or start a container
that mounts the whole home folder or runs `--privileged`. No token scope or
deny rule narrows that. A container engine's API grants all of it or none.

## Decision

The agent container never reaches the host's engine: no host Docker socket,
no `--privileged`, no devices. Instead it runs its own engine:

- **Rootless podman inside the agent container**, as `rob`, with
  `podman-docker` so `docker build` and `docker run` work as written.
- **Nested containers use the agent container's network** (`netns =
  "host"`). They need no tun device, and their traffic leaves the same way
  the agent's own does.
- **Image storage on a named volume**, `claude-dev-containers`, so images
  survive recreating the container. It also gives overlayfs a real
  filesystem to sit on.
- **A custom seccomp profile**, `seccomp.json` in this repo, generated by
  `make-seccomp`. It is Docker's default profile plus the syscalls a user
  namespace needs: `unshare`, namespaced `clone`, `setns`, `mount`,
  `umount2`, `pivot_root`, `keyctl`, and also `sethostname` and the new
  mount API (`open_tree`, `move_mount`, `mount_setattr`, `fsopen`,
  `fsconfig`, `fsmount`). Docker's default allows most of these only when
  the container holds `CAP_SYS_ADMIN`, and `keyctl` never.

## Consequences

- An agent can only reach containers it started itself. `docker ps` in
  here lists podman's containers, never `mail`.
- The seccomp change widens the agent container's attack surface. Creating
  a user namespace needs no capability, so the kernel's user-namespace code,
  which has had privilege-escalation bugs, becomes reachable from the agent.
  Keeping OrbStack updated is the mitigation. The mount and hostname calls
  still require `CAP_SYS_ADMIN` in the namespace they act on. `rob` holds it
  only inside user namespaces `rob` creates, never over the agent
  container's own mounts, hostname or network. `keyctl` reaches the kernel
  keyring, which Docker keeps closed because keyrings aren't namespaced;
  crun needs it for each nested container's session keyring.
- Docker masks parts of `/proc` in the agent container, and the kernel then
  refuses a fresh procfs mount inside a user namespace. A nested container
  depends on crun falling back to bind-mounting the agent container's
  `/proc`. If that fallback fails, `--security-opt systempaths=unconfined`
  on the run line would fix it, but it unmasks those paths. Adding it is a
  decision to record here, not a quick fix.
- Nested containers have no cgroup of their own: `/sys/fs/cgroup` is
  read-only in the agent container. So there are no CPU, memory or PID
  limits on them, and `docker stats` reports nothing.
- Nested containers share the agent container's network, so two of them
  can't bind the same port, and `-p` mappings are meaningless.
- Images built here are podman's, in the volume. The Mac's Docker doesn't
  see them, so the human rebuilds from the same Dockerfile.
- Linux hosts are not covered yet. There the agent container is itself
  rootless podman, and nesting rootless podman in that is a separate
  piece of work.

## Alternatives rejected

- **Host Docker socket**, directly or through a filtering proxy. Directly,
  it is root-equivalent on every container. A proxy that allowlists API
  calls has to understand `exec`, `create`, mounts and `privileged` well
  enough to be a security boundary of its own. That is a lot to get right,
  and nothing here would test it.
- **`--privileged` Docker-in-Docker.** It hands the agent container every
  capability and every device, so a mistake inside it reaches the VM.
- **A separate VM or builder service.** It is stronger isolation, but it
  is more machinery to run and keep in step, and agents need tight
  build-run-inspect loops.
